# M3.1 end-to-end test (for the owner)

Nothing in this document has been run by the assistant: M3.1 was verified with unit tests and the VSIX compile check
only, because starting Visual Studio from scripts disturbs the desktop. Please run it once before a release and fill in
the run record.

## Setup

1. Build and install the 0.4.0 VSIX (see [m2-manual-e2e.md](m2-manual-e2e.md)); the Output pane shows
   `VsMcpDebugger 0.4.0 ready (..., protocol 2.2)`.
2. Open **two** Visual Studios on two solutions that live in different folders, for example `samples/OrderDemo` in one
   and `samples/FaultDemo` in the other.
3. Open two terminals, one in each solution's folder, each running an agent (or the driver below).

## Driver (optional)

    dotnet run scripts/e2e/m3.1-two-instances.cs -- <repo>\src\VsMcpDebugger.Mcp\bin\Debug\net10.0\VsMcpDebugger.Mcp.dll <folder A> <folder B>

It starts two MCP servers with those working directories and prints `vs_instances`, `debug_status` from each, and a
state-changing call from agent B against agent A's Visual Studio. It has been compile-checked only.

## The six scenarios of the design (section 1)

| # | Action | Expected |
|---|---|---|
| 1 | Agent A (terminal in A's folder) calls `debug_start` with `project` set, without `vs_select` | A's Visual Studio starts that project; B's Visual Studio is untouched |
| 2 | At the same time agent B sets breakpoints and debugs in B's Visual Studio | neither disturbs the other |
| 3 | B calls any state-changing tool against A's Visual Studio (`vs_select` A's pid, then `bp_set`) | `in_use`, naming A and A's folder; nothing changed in A's Visual Studio |
| 4 | Edit a source file of the project, do not build, then `bp_set` in that file | the result has `warnings` with `stale_build`; a **Rebuild** bar appears in that Visual Studio |
| 5 | End debugging with `debug_stop`, look at Solution Explorer | the startup project is what it was before step 1 |
| 6 | Extensions > VsMcpDebugger > Disconnect AI | both agents are cut off at once; Reconnect AI re-enables connections |

## More checks

| # | Action | Expected |
|---|---|---|
| 7 | Start an agent in the repository root while the `.sln` is in `src\` and only one Visual Studio matches | it is chosen without `vs_select` |
| 8 | Start an agent in an unrelated folder and call any tool | an info bar asks to approve the connection; **Deny** gives `denied` / `user_denied` and changes nothing |
| 9 | Allow once, call several tools | no second question for that connection |
| 10 | The Rebuild bar: debug while the project is stale | no bar while the session runs or is at a breakpoint; it comes back after the session if still stale |
| 11 | Press **Rebuild** on the bar | the project is cleaned and rebuilt (check the Output window shows a clean and a build); the bar is gone; a new `bp_set` has no warning |
| 12 | Build the project by hand (Build menu) while the bar is up | the bar disappears when the build finishes |
| 13 | Close the bar with the x, then `bp_set` again | the bar does not come back until the project was up to date once and is stale again |
| 14 | `debug_start` with `project` set to a library project | `invalid_argument` listing the projects that can be started |
| 15 | `vs_release` from agent A, then agent B's `bp_set` | B succeeds |
| 16 | Close agent A's terminal while it holds the Visual Studio | the status bar stops saying "in use by ..."; B can use it at once |
| 17 | Look at the Visual Studio status bar and at `vs_instances` while A holds it | "in use by <client>" and `availability: in_use`, `heldBy`, `heldByFolder` |
| 18 | `vs_release`, `bp_list` | breakpoints set by A are still there and visible to B |
| 19 | Extensions > VsMcpDebugger > Copy MCP Setup Command, then paste into a text editor | two lines: `dotnet tool install -g VsMcpDebugger --prerelease` and `claude mcp add vsmcpdebugger -- vsmcpdebugger serve`; a message box explains the next steps |
| 20 | Extensions > VsMcpDebugger > Set Up AI Agent... on a machine where the tool is missing or older | a message box lists OK/MISSING lines and the exact commands; **No** changes nothing; **Yes** runs them, the status bar says "checking..." while it probes, a final box shows the new status; the Output pane "VsMcpDebugger" logs each command and its exit code |

## Risks the assistant could not check without Visual Studio

- **Startup project timing** (check 5): `debug_start(project)` switches the startup project, calls Go and switches it
  back at once. If Visual Studio reads the startup project after Go returns, the wrong project would start. If check 1
  starts the wrong project, this is why; the fix is to restore the startup project at the first mode change instead.
- **Rebuild** (check 11) uses the solution build manager with the clean and build flags; if it only builds, the flags do
  not combine as assumed.
- **Info bar look** (checks 8, 10) and **status bar text** (check 17).
- Visual Studio's own "up to date" answer is not used; staleness comes from file times only. A touched file with
  identical content counts as stale.
